# WorkBuddy：入住与人脸登记体验版实施发布任务（2026-11-24）

## 1. 本轮已确认的需求与授权范围

本轮由 WorkBuddy 负责实现、测试和发布微信小程序**体验版**，目标是能实际办理测试入住，再提交人脸登记。此卡不是既有功能已完成声明；根 Codex 当前只交付任务文档，未连接 WorkBuddy、创建实际派单或发布版本。

| 项目 | 本轮确定要求 |
|---|---|
| 测试入住 | 主入住人的测试流程直接通过；只限服务器配置的测试范围，不将正式住户审核改为自动通过 |
| 测试房号 | **102**；它是展示房号，须在本地后台绑定唯一项目/楼栋/roomId/houseId，不从多条同号房中默认取第一项 |
| 租期 | **上线时由负责人手动填写起止时间**，保存为服务端测试租约；不替用户选日期、不默认一年或长期，未填写时页面明确待配置 |
| 人脸入口 | 入住审核通过后可上传本人的测试人脸；上传页面自动取得房号与租期，不再次手填或信任客户端授权字段 |
| 有效期 | 用户已确认：**按租期起止，每天 24 小时通行**。不是登记后只生效 24 小时，也不是长期有效 |
| 通行范围 | 仅所选测试房间关联的测试设备/门；沿既有经核验的全天规则和明确门号，不扩到全部设备 |
| 发布渠道 | 新微信体验版，可供指定测试成员使用；不提交正式审核、不发布公开正式版 |

本轮允许为该测试链路实施必要的小程序、测试服务、受控本地任务接线及体验版发布。真实登记仅限明确加入测试范围的本人、102 关联测试设备与手填租期；实际动作仍通过既有设备身份/TLS/账号权限检查，不绕过失败门禁。不授权支付/退款、合同签署、远程开门、无关住户变更、批量设备操作或生产规则全局放宽。

## 3. 同一任务内补齐的用户流程

1. 登录后进入明确标识的“测试入住”，显示配置的 102 房及手填租期。房间尚未唯一绑定或租期未填时不能自动通过，不能悄悄退回其他房或长期。
2. 用户提交主入住申请。服务端从可信调用者身份取得当前用户，在事务内核对测试开关、测试账号名单、102 房间映射、租期与申请版本，并幂等写入住/租约快照和测试自动通过审计。客户端传 `approved=true/testMode/roomNo` 不能取得权限。
3. 入住通过后出现“上传人脸”。明确由本人确认本次照片用途；使用私有存储或等价的受控上传，文件绑定当前用户和入住申请。未通过、他人申请、他人文件、已取消/失效租约都不得创建有效登记任务。
4. 房号自动显示 `102`，数据来自服务端入住关联；稳定 ID 与展示号分别保存。有效期只读显示手填租期，UI 显示“租期内每日 24 小时”，不允许客户端另行提交门号、人员编号或扩大日期。
5. 服务端持久保存登记任务与稳定 employeeNo，绑定用户＋入住＋租约版本＋roomId＋测试设备/门；重复点击、重传或轮询不重复建人。派发前重新核对申请、文件归属、租期及配置版本。
6. 页面分别展示照片收件、等待下发、设备处理中、设备查询已确认、失败/结果待核，以及“待现场刷脸验证”。只有相应真实事实发生才推进，不把文件上传成功、CLI 退出 0 或 pending-site 显示成现场识别通过。

## 4. 测试隔离与设备接线的技术要求

- 测试自动通过由服务端默认关闭的配置控制，并绑定明确测试环境/数据域、测试账号、102 稳定房间 ID；测试账号通过本地管理员配置，不要求把 openid/凭据贴聊天。普通账号保持原审核流程。
- 微信体验版渠道或客户端布尔不能作为服务器审批依据。测试集合禁止客户端直接写审核、租期和人脸状态。优先独立测试云；复用现有云时须有可验证的测试命名空间/授权隔离，不能全局放开生产云。
- 旧 beta.18 是 `live` 指向既有云且 `allowDeviceOperations=false`，不代表有独立测试环境。不得只改这个前端开关为 true 来开放真实开门或人脸写入；保留普通远程开门关闭，仅开放本任务受控人脸流程。
- 云端不能直接访问现场私网门禁。若无现成合规通道，可实现本地受控 worker 主动领取云端测试任务，不开放公网管理端口、不反向暴露 admin loopback API，不让小程序运行 Node HTTPS adapter 或持有设备秘密。
- 本地执行器复用既有登记服务与受控设备配置。设备密码、预期 pin、私钥只留可信执行端；不得下发小程序、写入发布包或日志。普通 curl 的根不受信任结果不自动否定另一个已独立核验的 pin-only 通道；也不能拿合成 pin PASS 当作真实通道已证。
- 新小程序路径必须显式传 `validityMode: fixed` 和服务端租约 `validFrom/validTo`。若复用统一命令，真实设备动作须由 Windows 受控执行器另显式传 `mode: device`；`mode` 与 `validityMode` 不混用，不省略 mode 落入 simulation 后记作设备成功。simulation 只用于合成测试或明确标注的模拟。既有 PC 命令默认 unlimited 不改；新路径缺日期、租约不匹配或超设备能力范围即拒绝，不静默扩期或截断。
- 日期/时区沿现有租约规则，记录明确的 Asia/Shanghai 起止快照；日期型含首尾时正确映射设备边界，不能直接用隐式 UTC 偏移或增加一天。人脸入口不重算合同周年/28 日算法。
- 复用已核验全天模板读取、授权及查询确认，不把 unlimited 代替全天计划。设备结果未知时保留已有人员/请求事实与任务号，不盲目重试、换人员号或删除残留。

## 5. 实施、测试及发布顺序

同一 WorkBuddy 任务内完成实现到体验发布，不新增一般性的中间业务批准门。若缺负责人手填租期、测试成员授权或设备可信材料，先完成不依赖缺项的代码与编译，准确列出仅受阻部分，不伪造数据或结果。

1. **核当前平台**：用已有开发者工具登录检查项目权限、实际云环境、当前体验版本及可回退版本；历史登录、上传报告不能代替今天核对。需扫码/体验成员设置时由负责人在本机完成，不索取密码/token。
2. **列实施清单并开发**：必要变更限入住/人脸页面及路由、资料入口、API/测试配置、专用测试云服务/存储规则、本地 worker、相应测试、版本/发布与来源登记。先在任务记录列具体路径，自主在本范围实施；不修改无关登录/支付、旧 P2 行为或默认长期规则，不合并未批准业务分支。
3. **配置测试业务**：后台唯一绑定 102，负责人上线时填租期起止，指定测试账号及测试设备/门。不能用 `users.houses` 的第一项或历史 owners 手机号绑定冒充已审核租约。
4. **验证**：运行与变更匹配的合成测试及微信编译/预览，保存真实命令、退出码与原始结果，不搬用旧 246、51、54 等数字。云函数变更按项目要求登记 `docs/backend-changes.json` 的实际源哈希。
5. **测试服务部署**：只部署本任务实际变更的测试服务/规则，先记录原版本与回退方式；不整批覆盖云函数、不调用 dbInit/contentInit/chatInit/syncDevices 初始化真实数据。无法证明测试范围隔离时不把自动通过规则部署为生产全局能力，报告具体缺项。
6. **体验版发布**：固定受测源码完整 SHA、唯一新版本和包哈希，按项目工具打包、编译、上传并在平台指定体验版；不重复上传旧 beta.18，不提交正式审核、不公开发布。上传前确认源码/包/云服务版本相互对应和回退锚点。
7. **指定成员真机测试**：负责人从平台授权的体验入口实际登录，完成 102 入住自动通过→照片上传→房号自动展示→租期全天计划展示→登记状态查询。设备材料及本地 worker 可用时只对本测试身份执行必要登记与查询，不调用远程开门；现场刷脸由本人完成并单独记结果。

## 6. 必须有的验收事实

| 项目 | 真实判据 |
|---|---|
| 自动通过 | 指定测试账号/102 在配置有效时通过；普通账号、伪造 approved/testMode、错房及失效配置不能绕过审批 |
| 房号 | 从服务端唯一入住关联自动取得；更改客户端房号不改变登记目标，多条歧义不默认取第一条 |
| 租期 | 手填后持久快照与人脸任务一致，明确 fixed；未填/过期/取消/越界不回退长期，全天与长期区分 |
| 上传与归属 | 仅本人通过的申请能创建有效照片/登记任务，跨用户/文件伪造被拒，设备秘密不进入小程序 |
| 幂等与竞态 | 重复提交不会重复建人，租期或审批在排队后变化时重新校验；未知结果不伪报成功或自动重发 |
| 测试范围 | 关闭测试开关后新自动通过停止，普通用户不受影响；全局开门开关仍关闭 |
| 发布可用 | 平台实际版本、体验成员和可用体验入口均核对，真机结果单列；上传/编译成功不等于上述流程通过 |
| 设备与现场 | 明确区分平台收件、设备查询确认和现场本人刷脸；未执行部分按实际待处理/阻断记录 |

回退优先恢复体验版本并关闭新增测试入口/自动通过/派发配置，不自动删除任何既有人脸/人员/权限。记录本次新建测试对象，保留原报告、旧工件和新旧引用；权限按本次租期固定到期，不默默延长。涉及已登记对象的额外清理另报告具体范围，不擅自操作正式住户。
