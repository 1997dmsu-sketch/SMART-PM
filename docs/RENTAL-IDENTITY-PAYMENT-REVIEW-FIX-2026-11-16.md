# 预签约身份证材料变更与支付资格修复证据

- 日期：2026-11-16。
- 原始输入：`8df281beb4e61c5229aa506fbfa8ed5031d4e71b`；分支 `feat/rental-reservations-presigning`。
- 原缺陷：`paymentParams` 只读待支付订单状态及截止时间。订单创建后重传正反面虽将预约重置为 pending，旧订单仍可取得支付参数。
- 本轮为追加修复，不合并 main，不部署，不收款，不操作生产云/设备；没有启动 HTTP 监听。实际修复 SHA 见交付回报。

## 修复合同

1. 材料重传、当前自有待支付订单标记 `identity_changed`、释放该订单付款占位在同一事务完成；事务复查预读占位指针，发生并发变化即拒绝，不释放其他订单的占位。
2. 旧订单即使重新审核通过也不能恢复支付。新合同/新订单必须绑定新材料 ID；旧订单保留原合同和金额快照。
3. `paymentParams` 在事务内核验当前订单、占位、预约确认状态、审核状态、正反面 ID、归属、side、有效期和密文存在性；失败在调用支付适配器前拒绝。生成预支付参数后再次复核再返回，覆盖适配器请求期间材料变更。
4. 已交付客户端的支付参数无法靠本地状态撤回，因此支付到账事务也复核上述材料绑定；材料变化后的到账进入 `refund_required`，不生成留房、不夺取新占位，不适用“留房超时不退”政策。
5. 已核验付款且有效留房或已签约时，直接重传被拒绝，须由物业处理材料变更；不自动重签已付款合同。
6. 新状态在用户端/后台可见，用户仍可核对支付状态；不能将客户端成功提示直接标记为已支付。

## 新增回归

| 场景 | 结果 |
|---|---|
| 正面/反面分别重传后调用旧单 paymentParams | 409，支付适配器调用 0，失败请求前后全库 deepEqual |
| 新材料重新审核通过后重用旧订单 | 仍为 409；新确认的新单可继续支付 |
| 旧版本遗留 awaiting_payment，绑定被替换/审核 pending/rejected/预约被拒绝/材料过期或清除 | 每个场景 409、适配器调用 0、全库 before/after 独立快照相等 |
| 支付适配器生成参数时发生材料重传 | 返回参数前复核失败，不将新参数返回客户端 |
| 客户端已缓存旧参数，重传并创建新单后收到旧单到账 | 旧单需退款，新单及其占位不变；重复通知不夺取/延长占位 |
| 付款先提交，随后尝试重传 | 重传 409、全库不变，保留已付款合同 |
