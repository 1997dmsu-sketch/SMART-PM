## 2. 使用者与现有角色的区别

| 业务使用者 | S 的实际权限模型 | 仍需明确的业务范围 |
| --- | --- | --- |
| 系统管理员 | 后台 `admin`；账号、审计及新测试配置入口另有服务端限制 | 项目间授权、双人复核、关键配置审批是否需要 |
| 内容/房源运营 | 后台 `editor` 可写 houses、content、uploads；不能写 users、rooms 或物业目录 | 是否增加员工岗位，以及可维护哪些楼栋/客户 |
| 只读成员 | 后台 `viewer` 可读业务资源，无写入权限；不能读管理员账号/审计 | 客服、财务是否应看到不同字段与范围；维修岗位随报修暂缓 |
| 财务、现场运维 | 当前后台 role 不等同这些业务岗位；不能以名称相近代替权限设计 | 财务退款、抄表、设备运维分别授权待确认；维修工单授权随报修暂缓 |
| 小程序租客/管理员 | 云端 users 身份，与电脑后台账号体系分别维护 | 不得由后台登录成功推断已获得某租客或微信身份 |

上述代码依据为 `S:admin-web/lib/model.mjs:L11–L23`、`S:admin-web/server.mjs:L262–L280`。菜单隐藏不是认证边界；静态 HTML 可读取与私有 API 是否授权是两个问题。

## 3. 物业与房源维护

### AP-001 项目、小区、楼栋、楼层及房号建档

- 关联旧项：PROP-01、PROP-02、OPS-01；既定层级已确认，具体员工建档职责仍待确认。
- 需求：维护可追溯的层级及稳定 ID；房号、户型编码、住户/门锁房产编号分别建模。
- 现状：`M:docs/PROPERTY-MODEL.md:L5–L10`；`S:admin-web/lib/property.mjs:L22–L47、L60–L98` 有层级读取及小区/楼栋事务创建。
- 缺口：这些目录记录不能证明已完成真实项目资料核对，地址、产权用途和人员维护责任不能从测试名称推导。
- 建议验收：新建/重名/父级错误逐项验证；失败全量零变化；刷新、重新登录与恢复备份后 ID 不变。
- 边界：物业服务可使用 LocalStore/CloudStore；本轮不建真实楼栋、不导入云数据。

### AP-002 户型目录与跨房间应用

- 关联旧项：PROP-01、PROP-02；名称和编码分离已确认，新增户型业务字段待确认。
- 需求：楼栋内编码唯一；选择所属楼栋户型，批量应用时同步关联展示记录。
- 现状：`S:admin-web/lib/property.mjs:L100–L144、L359–L413` 校验目录并在事务内更新 rooms/关联 houses。
- 缺口：已有房源关联变更、跨楼栋应用及冲突恢复需要分别验收；不能把可维护户型等同完整租赁产品配置。
- 建议验收：同栋重复编码拒绝、异栋允许；跨栋整批拒绝；部分关联损坏时整批不留下半更新。
- 边界：批量上限及 refs 预算沿实现验证，不在此批准新迁移/回填任务。

### AP-003 楼层、房号批量生成与维护

- 关联旧项：PROP-02、OPS-01；现有工作流有代码，扩展编号规则待确认。
- 需求：先预览再提交；保留人工房号与历史稳定编号，反馈新增、跳过、失败的实际范围。
- 现状：`S:admin-web/lib/property.mjs:L161–L257、L258–L307`；`M:docs/PROPERTY-MODEL.md:L48–L54` 描述分批生成及既有房间处理。
- 缺口：多批次不等于整个计划单一事务，失败后的继续位置、取消与完整性证据必须另列。
- 建议验收：含跳号/地下层/重复提交的计划；中途失败后安全续作；已存在房间租金、户型及绑定不被覆盖。
- 边界：批量建档不会自动上架，不以“生成成功”代表房源已可预约。

### AP-004 出租展示、上下架及真实房间关联

- 关联旧项：PROP-02、PROP-03、OPS-01；房源运营细则来源不足，待业务确认。
- 需求：房间档案与展示房源分开；维护租金、面积、图集、展示状态及唯一房间关联。
- 现状：`S:admin-web/lib/model.mjs:L55–L74`；`S:admin-web/lib/property.mjs:L415–L465`；状态有在租/已租/下架。
- 缺口：该状态模型不是“已预约/付押金/租赁生效”的完整库存状态机，不能据此自动承诺留房。
- 建议验收：上架/下架影响列表与详情；重复关联拒绝；历史独立房源保留；已关联房源不能偷偷换房。
- 边界：价格必须来自授权配置；未知价格不能填零或借用样本金额对外签约。

### AP-005 公共用房与展示可见性

- 关联旧项：PROP-01、PROP-03、AUTH-01；沿用既有公共用房语义，新展示政策待确认。
- 需求：区分“公共用房”与“允许公开展示”；列表、总数、分页、详情使用一致限制。
- 现状：`S:admin-web/lib/property.mjs:L384–L405` 同步 isPublic；`S:cloudfunctions/getHouses/index.js:L13–L46` 查询限制与分页；预置另用 listingVisible。

- 建议验收：伪造筛选、直接详情 ID、翻页及旧链接均不能返回被隐藏记录；后台仍可按权限维护。
- 边界：isPublic=false 不等于可上架或可预约，不依据这一字段开放首层测试房间。

## 4. 账号、人员与岗位

### AP-007 人员与房屋绑定、解绑及交接

- 关联旧项：TEN-01、TEN-02、AUTH-01、PROP-01；入住承接已确认，续退租及家庭授权细则待确认。
- 需求：绑定合法房产编号，追踪人工变更；解绑、换房及租期结束不因再次登录恢复旧权限。
- 现状：`S:admin-web/server.mjs:L726–L761` 限定绑定/解绑并写 housesManaged；`M:docs/ADMIN-WEB.md:L74–L80` 说明配套 phoneLogin。
- 缺口：此处是用户房产数组维护，不是完整入住/续租/退租/家庭关系及设备权限同步工作流。
- 建议验收：不存在房产不能新增绑定、历史缺房产可解绑；再次登录保留人工绑定；跨用户变更须服务端授权并留审计。
- 边界：管理员手工绑定不等于已付款、已签约或自动获得门禁权限。

### AP-008 租客身份归一与两种登录方式

- 关联旧项：AUTH-01、TEN-01；最新用户确认手机号自动注册/复用并保留账号密码登录，不扩大业务实名承诺。
- 需求：微信服务端验证手机号后自动注册/复用用户；后台给既有已验证身份开密码并关联本人微信，房屋/角色权限不自动授予。
- 现状：`S:cloudfunctions/phoneLogin/index.js:L11–L41` 已有服务端手机号验证及身份复用；`S:cloudfunctions/accountLogin/lib/service.js:L65–L144` 和 `S:miniprogram/services/api.js:L287–L370` 仍有旧码/密码登录。
- 缺口：prepare/开户码须移除；phoneLogin 的旧 owners 条件导入房屋须按最新授权边界核对；指定账号尚未创建，新流程现网可用性未证实。
- 建议验收：同一身份两入口一致；仅服务端验证手机号事实可注册；phone/微信唯一性冲突失败关闭，错微信/禁用/错密码统一失败。
- 边界：取消获取开户码功能，不留 UI/prepare 旁路；密码不进存储/日志。注册不依赖商户，手机号验证不等于实名材料审核。

### AP-009 电脑后台账号、启停及本人改密

- 关联旧项：AUTH-01、OPS-01、AUD-01；现有三角色已实现，岗位制度待确认。
- 需求：独立后台账号开通、改密、停用及权限变更；不能通过修改自己的账号绕过控制。
- 现状：`S:admin-web/lib/auth.mjs:L10–L25、L54–L102`；`S:admin-web/server.mjs:L573–L609` 有改密及账号维护。
- 缺口：live 的管理员账号仍在服务端文件；多实例账号、共享会话及集中限流不由 CloudStore 自动提供。
- 建议验收：停用/权限 revision 变化使旧会话失效；最后管理员/自改权限限制按实际规则核对；备份恢复不泄漏哈希。
- 边界：后台密码规则与租客账号规则分别验证；不能把前者 12 字符下限误写成当前租客 8 字符规则。

### AP-010 租客账号开通、重置及启停后台

- 建议验收：非 admin/未验证用户/重名/身份歧义拒绝；不采信客户端自报 phone/OpenID；重置后旧密码失败，DTO/审计不含秘密。
